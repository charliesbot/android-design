# Wear OS in the previewer

**Date:** 2026-11-04

## TL;DR

The previewer draws Wear OS proposals with Google's real Wear Compose components. Wear Compose ships only as Android libraries, so the app compiles Google's own source code for Compose Multiplatform desktop, with small stand-ins (shims) for the Android-only parts. Upstream source is never edited, so an upgrade replaces it wholesale with a script. A second catalog, two round watch views and a Wear theme sit on top, and every existing path (live window, headless renders, `check_proposal`, `get_tree`) handles both surfaces. `app/wear/README.md` is the operational reference: every shim, every excluded file, and the known fidelity gaps.

This is the first of three Wear deliveries. Kotlin export and promoting Wear in the skills and evals come next.

## Why port the source

The goal is the same as the phone previewer's (`visual-design-exploration-v3.md`): the real component, live, with no compile step during iteration. Wear Compose (`androidx.wear.compose`) is published only as Android AARs, with no desktop variant, so it cannot be a normal dependency of a macOS app.

A spike on 2026-11-04 measured the source of 1.8.0-alpha03: about 86% of its files are plain Compose, and the rest touch Android in a few known ways (context and settings, curved text drawn with `android.graphics`, haptics, dialogs' window). Every Compose API it uses exists on desktop except about a dozen platform ones. Its dependency versions matched the app's Compose Multiplatform 1.13.0-beta01. The spike's render matched a render of the same code on real Android (Robolectric) apart from the typeface.

Rejected alternatives:

- **Lookalike components drawn with phone Compose:** they drift exactly where Wear differs most (curved time text, the scaling list, the edge button), which fails the fidelity bar.
- **Rendering on Android (Robolectric or layoutlib) and showing images:** real components, but a static image per edit instead of a live window.
- **Streaming a Wear emulator into the window:** live and fully real, but heavy, always running, and still video frames.

## How it is built

### The port (`app/wear/compose`, module `:wear:compose`)

- `upstream/` holds Google's sources for four artifacts: `compose-foundation`, `compose-material-core`, `compose-material3` and `compose-navigation3`. These are what a Wear app uses for Material 3 Expressive screens (the `wear-compose-m3` skill names Navigation 3 for new navigation). `compose-material` (Material 2.5), `compose-navigation` (the older NavHost), `compose-ui-tooling` and Tiles (`protolayout`) are out.
- `src/shims/` makes upstream compile and run on desktop. A shim lives in the same package as what upstream imports (for example `android.os.Build` or `androidx.compose.ui.platform.LocalContext`), so upstream needs no edits. When a file cannot be shimmed, the build excludes it and, where needed, a desktop copy in the shims tree replaces it (curved text drawn with Skia, for example).
- `src/generated/` holds `R.kt`, generated by the sync script from the material3 AAR (English strings, plurals, drawable ids).
- `src/host/` is the only API the rest of the app adds to upstream's: `WearDevice(widthDp, heightDp, round)` provides the screen size and shape and clips to a circle, and `dynamicWearColorScheme` runs Wear's own watch-face color mapping on supplied colors.

### The catalog and views

`Catalog` is an interface with two implementations, `M3ExpressiveCatalog` and `WearCatalog`. Each owns its components, views, size breakpoints, color and type roles, and the facts the findings need. Code that is not specific to one surface asks the proposal's catalog instead of naming one.

- **One surface per proposal.** Every screen of a proposal uses the same catalog, the way a real project keeps its Wear app in its own module. Mixing is a validation error.
- **Views:** `watch` (204 dp) and `watch-large` (227 dp), both round and dark. Google asks to design for the smallest round screen first and adds a breakpoint at 225 dp, so Wear size overrides use one key, `large`, applied from 225 dp.
- **Rules:** no panes, Wear color and type roles, a 48 dp touch target.

### Rendering

The shared host (back stack, local state, actions, layout tree recording, the headless renderer, the confined window frame) is reused, not forked. `ProposalPreview` is the one place the preview splits by catalog: a watch view runs the Wear theme, a `WearDevice` and Navigation 3 with Wear's swipe-to-dismiss scene. Per node, `RenderComponent` hands Wear nodes to the Wear renderer, which maps each catalog component to its upstream composable. The time text always shows 10:09 through the public `TimeSource` parameter, so renders are comparable.

### Theme

- **Color:** with no seed, Wear's default scheme. With a seed, the app builds tonal palettes from it and feeds them to upstream `dynamicColorScheme` through the shims, so the mapping from palette to Wear roles is Google's and not a copy. Explicit role overrides apply on top.
- **Type:** Roboto Flex everywhere, bundled, as Google specifies for Wear. The owner's Google Sans Flex standard covers phone, tablet and desktop only.
- **A shared DESIGN.md:** one project has one DESIGN.md for its phone and Wear apps. Its seed and the color roles Wear has apply to Wear. Its typography does not, and a style that uses a phone-only role is unavailable to Wear screens.

## Upgrading Wear Compose

1. **Check version alignment first.** Read the new version's `.module` files on Google Maven (`https://dl.google.com/android/maven2/androidx/wear/compose/<artifact>/<version>/<artifact>-<version>.module`). Its required Jetpack Compose versions (`foundation`, `ui`, `runtime`, `animation`) must not be newer than what the app's Compose Multiplatform version provides, and its `navigation3` requirement must not be newer than the app's `navigation3` version in `app/gradle/libs.versions.toml`. If they are newer, upgrade Compose Multiplatform first, or wait.
2. Run `python3 scripts/sync_wear_compose.py <version>`. It replaces `upstream/` and regenerates `R.kt`.
3. Run `cd app && ./gradlew build spotlessCheck`. Fix failures with shims or exclusions, never by editing upstream. Record each new shim or exclusion in `app/wear/README.md`.
4. Look at the test renders in `app/wear/compose/build/renders/` and at a Wear fixture rendered with the CLI.

A new upstream Android-only API usually needs one more stub. A whole new component that depends on Android graphics or windows is excluded until a desktop replacement is worth writing.

## Known gaps

- Crown (rotary) input is not simulated. Sending a rotary event on desktop requires calling Compose internals by reflection, which this project does not allow. The mouse wheel scrolls lists normally.
- Wear lists are lazy, so the layout tree and findings cover only the items on screen.
- Curved text has no kerning or glyph warping. API-gated upstream branches are off (`SDK_INT` is shimmed to 30). Strings are English only. Pickers, `OpenOnPhoneDialog`, `AnimatedText` and `curveToEdge` are excluded.
- No finding yet flags content clipped by the round edge, and Wear has no `primary` marker for the one-primary-action rule. Both are planned with the Wear evals.
- Kotlin export rejects Wear proposals until the export delivery.
