# Wear OS in the previewer

**Date:** 2026-11-04

## TL;DR

The previewer draws Wear OS proposals with Google's real Wear Compose components. Wear Compose ships only as Android libraries, so the app compiles Google's own source code for Compose Multiplatform desktop, with small stand-ins (shims) for the Android-only parts. Upstream stays byte-identical to Google's release, so an upgrade replaces it wholesale with a script. A second catalog, two round watch views and a Wear theme sit on top, and every existing path (live window, headless renders, `check_proposal`, `get_tree`) handles both surfaces. `app/wear/README.md` is the operational reference: every shim, every excluded file, and the known fidelity gaps.

Kotlin export for Wear proposals is described under Kotlin export below.

## Why port the source

The goal is the same as the phone previewer's (`visual-design-exploration-v3.md`): the real component, live, with no compile step during iteration. Wear Compose (`androidx.wear.compose`) is published only as Android AARs, with no desktop variant, so it cannot be a normal dependency of a macOS app.

A spike on 2026-11-04 measured the source of 1.8.0-alpha03: about 86% of its files are plain Compose, and the rest touch Android in a few known ways (context and settings, curved text drawn with `android.graphics`, haptics, dialogs' window). Every Compose API it uses exists on desktop except about a dozen platform ones. Its dependency versions matched the app's Compose Multiplatform 1.13.0-beta01. The spike's render matched a render of the same code on real Android (Robolectric) apart from the typeface.

Rejected alternatives:

- **Lookalike components drawn with phone Compose:** they drift exactly where Wear differs most (curved time text, the scaling list, the edge button), which fails the fidelity bar.
- **Rendering on Android (Robolectric or layoutlib) and showing images:** real components, but a static image per edit instead of a live window.
- **Streaming a Wear emulator into the window:** live and fully real, but heavy, always running, and still video frames.

## How it is built

### The port (`app/wear/compose`, module `:wear:compose`)

- `upstream/` holds Google's sources for four artifacts: `compose-foundation`, `compose-material-core`, `compose-material3` and `compose-navigation3`. These are what a Wear app uses for Material 3 Expressive screens (the `wear-compose-m3` skill names Navigation 3 for new navigation). `compose-material` (Material 2.5), `compose-navigation` (the older NavHost), `compose-ui-tooling` and Tiles (`protolayout`) are out.
- `src/shims/` makes upstream compile and run on desktop. A shim lives in the same package as what upstream imports (for example `android.os.Build` or `androidx.compose.ui.platform.LocalContext`), so upstream stays byte-identical. When a file cannot be shimmed, the build excludes it and, where needed, a desktop copy in the shims tree replaces it (curved text drawn with Skia, for example).
- `src/generated/` holds `R.kt`, generated by the sync script from the material3 AAR (English strings, plurals, drawable ids).
- `src/host/` is the only API the rest of the app adds to upstream's: `WearDevice(widthDp, heightDp, round)` provides the screen size and shape and clips to a circle, and `dynamicWearColorScheme` runs Wear's own watch-face color mapping on supplied colors.

### The catalog and views

`Catalog` is an interface with two implementations, `M3ExpressiveCatalog` and `WearCatalog`. Each owns its components, views, size breakpoints, color and type roles, and the facts the findings need. Code that is not specific to one surface asks the proposal's catalog instead of naming one.

- **One surface per proposal.** Every screen of a proposal uses the same catalog, the way a real project keeps its Wear app in its own module. Mixing is a validation error.
- **Views:** `watch` (204 dp) and `watch-large` (227 dp), both round and dark. Google asks to design for the smallest round screen first and adds a breakpoint at 225 dp, so Wear size overrides use one key, `large`, applied from 225 dp.
- **Rules:** no panes, Wear color and type roles, a 48 dp touch target, a `primary` marker on the Wear buttons (Button, CompactButton, IconButton, TextButton, EdgeButton) for the one-primary-action rule, and the `round-edge-clipped` finding. That finding flags a control or text whose bounds reach past the circle inscribed in a round view. It skips anything inside a scrolling `Screen` or an `AlertDialog` (the tree marks both with `scrolls`: the dialog's content is a scrolling list upstream, so its buttons scroll clear), anything behind a modal, and the components in `WearCatalog.roundEdgeNames` (EdgeButton, TimeText, the progress rings). A text is judged by the box its drawn lines cover (`text.ink` in the tree), so a centered title in a full-width box passes when its glyphs fit; a control is judged by its bounds. A progress ring takes a band at its own edge: it records `ring: {padding, stroke}` in the tree (Wear's `CircularProgressIndicatorDefaults.FullScreenPadding` and the stroke width the renderer passes, in dp). A node whose center lies inside a ring must keep its corners inside the ring's inner circle, so a ring above an edge button counts as well as one that fills the view; the finding says the node "reaches N dp into the progress ring". The finding reads the recorded values, not constants of its own.

### Rendering

The shared host (back stack, local state, actions, layout tree recording, the headless renderer, the confined window frame) is reused, not forked. `ProposalPreview` is the one place the preview splits by catalog: a watch view runs the Wear theme, a `WearDevice` and Navigation 3 with Wear's swipe-to-dismiss scene. Per node, `RenderComponent` hands Wear nodes to the Wear renderer, which maps each catalog component to its upstream composable. The time text always shows 10:09 through the public `TimeSource` parameter, so renders are comparable.

### Theme

- **Color:** with no seed, Wear's default scheme. With a seed, the app builds tonal palettes from it and feeds them to upstream `dynamicColorScheme` through the shims, so the mapping from palette to Wear roles is Google's and not a copy. Explicit role overrides apply on top.
- **Type:** Roboto Flex everywhere, bundled, as Google specifies for Wear. The owner's Google Sans Flex standard covers phone, tablet and desktop only.
- **A shared DESIGN.md:** one project has one DESIGN.md for its phone and Wear apps. Its seed and the color roles Wear has apply to Wear. Its typography does not, and a style that uses a phone-only role is unavailable to Wear screens.

## Kotlin export

`export_kotlin` and the `export` command write Wear Compose Material 3 for a Wear proposal, in `core/domain/.../export/wear/` next to the phone exporter, with the same layout: the theme, the Navigation 3 host for a full export, one `@Composable` per screen with a `@Preview` at each watch size (204 and 227 dp), then the helpers the screens call. The code targets the release in `app/wear/compose/upstream/VERSION` (`WearExporter.WEAR_COMPOSE_VERSION` repeats it in the file header).

- **Frame:** `AppScaffold` sits once at the app root with `TimeText`; each screen is a `ScreenScaffold`. `scroll` on writes a `TransformingLazyColumn` with `rememberTransformingLazyColumnState` and `rememberTransformationSpec`, each child an `item` with the `transformedHeight` modifier and, where the component takes one, `SurfaceTransformation`, exactly as the renderer applies them. `scroll` off writes a `Box` that ends above the edge button, with a small `FixedScrollInfoProvider` object so the scaffold gives the button its full height. The edge button goes in the scaffold's slot. A screen with `timeText` off passes an empty `timeText` to its scaffold.
- **Navigation:** a route key per screen and a `NavDisplay` with Wear's swipe-to-dismiss scene, built like the phone host. Opening a dialog is state in the screen (`showX`), not navigation.
- **Theme:** `WearAppTheme` lists every Wear color role as a literal `Color(0xFF......)`, the values the previewer drew for the proposal's seed, role overrides and DESIGN.md colors. The scheme is computed in the desktop renderer (`WearThemeResolver.roleColors`), which `core:domain` cannot depend on, so the app's export path (`KotlinExport` in `:app`, used by MCP and the CLI) resolves it and passes it to `KotlinExporter.export` as a `WearColors`. Typography is Wear's default, so no font files.
- **Size overrides:** a `large` override writes an `if (isLarge)` over the two variants; `isLargeDisplay()` tests the screen width against 225 dp.
- **Data:** a screen's `dataModel`, bindings and templates export as the phone export writes them (`ScreenEmitterBase`): data classes, a `private object` of sample values, screen parameters, and bound text, icon names, flags and numbers. A template in the scrolling `Screen` is one `items(list) { x -> ... }` (`itemsIndexed` when it shows `@index`), each item with the same height transformation as a listed child; a template in a `Column`, `Row`, `Box` or `Card` is a `forEach`. Bound enums and `weight` are not read from data.
- **Not exported yet:** DESIGN.md typography overrides.

## Upgrades

Because upstream stays byte-identical, an upgrade replaces it wholesale with `scripts/sync_wear_compose.py` and then fixes the shims. The steps, including the version-alignment check that comes first, are in `app/wear/README.md` (Upgrading). A new Android-only API usually needs one more shim; a new component that depends on Android graphics or windows is excluded until a desktop replacement is worth writing.

## Known gaps

- Crown (rotary) input is not simulated: sending a rotary event on desktop needs Compose internals by reflection, which this project rules out. The mouse wheel scrolls lists in the window; the headless render scrolls a scrolling list from top to end itself, so the layout tree and its findings cover every item and the edge button, and `render` writes an end-of-list PNG (`app/wear/README.md`, "Lazy lists and the layout tree").
- Rendering fidelity gaps (curved text, API-gated branches, excluded components) are listed in `app/wear/README.md`.
