# Repository Purpose

This is the home of the `android-design` and `android-design-explore` agent skills: Material 3 Expressive design judgment for Jetpack Compose, and exploration built on it in a native previewer app. The repository holds the skills, the previewer app, the research the skills are distilled from, and the evals that check them.

**Scope status:** phone, tablet, desktop, and Wear OS app screens are the validated target, with Wear eval cases. Wear tiles, watch faces, and widgets are out of scope: the guidance exists (references and research) but its results do not yet meet the quality bar, so the skills mark it out of scope, with no eval cases and no widget catalog. The previewer draws and exports Wear proposals (`docs/design/wear-os-previewer.md`). Raising tiles and widgets is future work: improve the references, add eval cases and a widget catalog, and widen the skills' descriptions once their renders pass.

It is charliesbot's personal repository. Optimize for the owner's workflow, not broad applicability.

## Layout

- `skills/android-design/` is the installable design judgment skill (`SKILL.md` and `references/`): building, refining, and reviewing real Compose.
- `skills/android-design-explore/` is the installable exploration skill (`SKILL.md` and `references/`): proposals written for the previewer app, checked through its MCP server, and ported to Compose. It builds on `android-design`.
- Chai installs both from `skills/`, so keep anything that is not skill content out of these folders.
- `app/` is the previewer app, a standalone Gradle build (Compose Multiplatform, macOS): it draws proposals live, serves MCP over stdio, and renders headlessly for the evals. Its component registry (`app/core/model/.../Catalog.kt`) is the single source of truth for the catalog; `app/schemas/` holds the generated catalog and proposal schemas. `docs/design/visual-design-exploration-v3.md` records why it exists and how it is built.
- `app/wear/compose/` is the Wear Compose port: Google's `androidx.wear.compose` sources compiled for desktop. `upstream/` stays byte-identical to Google's release, so fixes go in shims or exclusions. Read `app/wear/README.md` before changing or upgrading the port.
- `docs/research/` holds the distilled research the skill is built from. `docs/research/source-coverage.md` is the page-by-page ledger of every official source and whether its guidance reached the research docs.
- `evals/` checks that agents following the skill still produce screens that meet its rules. See `evals/README.md`.
- `evals/compose-starter/` is the Compose sandbox for the manual export check (`evals/README.md`). It is where the export check renders exported Kotlin, not a template proposals start from: a proposal is a JSON file the previewer app draws. `evals/verify/verify.proposal.json` uses every catalog component; the export check verifies `compose-mapping.md` rows with it.
- `sources/` holds every official source page as fetched Markdown, one file per page at `sources/<domain>/<route>.md`. It is generated by `scripts/fetch.py`; never edit it by hand.

## Sources

Every rule in the skill must trace back to an official Google source: m3.material.io, developer.android.com/design/ui, the official Material and Android videos, and design.google articles. Apps built by other developers, including Google's own apps, are examples, not rules.

When a source changes or a gap is found, update the research docs first, then the skill, then the matching ledger rows.

Distill from the files in `sources/`, not from memory or a fresh web fetch, so every claim can be checked against a committed copy.

## Updating from upstream

1. Run `python3 scripts/fetch.py` (about 90 seconds; `--only m3,blog,design-ui,articles,videos` for a subset). Output is deterministic, so any change in `git diff --stat sources/` is a real upstream change.
2. For each changed page, read its diff and update the research docs, then the skill, where the guidance changed. Deleted pages usually moved; find the new route before dropping anything.
3. Run `python3 scripts/check_coverage.py`. It fails when a distilled ledger row has no source file or a source file has no ledger row. Give each new page a row with a verdict.
4. Commit `sources/` together with the research and skill changes it caused, so the history shows what changed upstream and what it changed here.

Fetch monthly and after major Material or Android announcements. Quarterly, look for new design.google articles and official talks: `fetch.py` fetches those from fixed lists, so it cannot discover new ones. If a fetch stops because it got far fewer pages than are saved, check whether the site's format changed before rerunning with `--allow-shrink`.

## Deliberate decisions

These are settled. Don't flag them in reviews unless the reasoning no longer holds.

- **Google Sans Flex for plain text; a curated brand set for display and headline** is the owner's standard, not Google's; the skill says so, and the eval rubric enforces it on purpose. Plain text (Title, Body, Label) is always Google Sans Flex. One optional bundled brand face (Fraunces, Bricolage Grotesque, Big Shoulders Display, or Doto at display sizes only) may take Display and Headline, following Material's brand/plain typeface split, and Google Sans Code serves numbers and data. Every face is bundled so explorations never fetch fonts.
- **Rules come from Google's docs, not apps.** Shipped apps, including Google's own, are examples of one implementation. A pattern seen in an app becomes a rule only when a Google source states it.
- **Git is the source inventory.** `sources/` files carry no dates or hashes so unchanged pages diff clean; commit history records when each page changed.
- **The coverage check proves agreement, not freshness.** A pass means the ledger and `sources/` match. Only running `fetch.py` shows whether Google changed anything.
- **AI glasses, cars, TV, and XR are out of scope.** Their routes are listed as skipped in the ledger and never fetched.

## Verification

After changing either skill, run the evals (`evals/README.md`). After changing a skill's `description`, run the trigger evals (`evals/README.md`, Trigger evals). After changing the rubric, run `evals/calibrate.py` first. After changing `evals/`, run `python3 -m unittest discover evals`. After changing `scripts/`, run `python3 -m unittest discover scripts`. After changing the app, run `cd app && ./gradlew build spotlessCheck`. To upgrade Wear Compose, follow `app/wear/README.md` (Upgrading). After changing the catalog registry, run `cd app && ./gradlew :core:domain:writeSchemas`, commit `app/schemas/`, and give each new component a row in `skills/android-design-explore/references/compose-mapping.md` (`python3 -m unittest discover scripts` fails until it has one). After changing the material3 version of `evals/compose-starter/`, run `python3 scripts/material3_inventory.py` and fix `skills/android-design-explore/references/compose-mapping.md` until `python3 -m unittest discover scripts` passes. After changing `compose-mapping.md`, the app's exporter, or the material3 version, run the manual export check in `evals/README.md`.

## Prose

No em-dashes anywhere in this repo's prose (`SKILL.md`, references, docs, `README.md`, and code comments). `sources/` is Google's text verbatim and is exempt. Rewrite the sentence with a comma, colon, period, parentheses, or conjunction, whichever it actually wants. Never do a blind character substitution.

## Project documentation

- `docs/PRD.md`, when present, defines the project direction and north star.
- `docs/ARCHITECTURE.md`, when present, describes the current system.
- `docs/design/`, when present, contains focused design documents.
- `docs/research/`, when present, contains external API, platform, and technical research.
- `docs/archive/`, when present, contains non-current documents and is historical context only.

Other project documents can live directly under `docs/`. Use lowercase kebab-case
filenames except for the fixed `PRD.md` and `ARCHITECTURE.md` names.
